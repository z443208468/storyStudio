# P2 计划编制及变更规则

本版取代旧版要求每个命令、参数、修复都逐行追溯授权的规则。计划必须服务实际生产，不能服务自身验收膨胀。

每个阶段只需说明：目标、真实前提、输入、操作顺序、可写范围、输出、验证、Controller 条件和失败后从哪里恢复。重大外部事实引用固定源码或官方资料；自选工程方案标为工程选择，不编造“作者要求”。

优先顺序：数据与授权安全 → 方法/Canon 保真 → 真实功能 → 可读作品 → 可重复运行 → 非必要整洁。已确认的阻塞要给出修复路径，不把已知坏版本永久锁死。实现 bug 与方法变化按实际作用区分，而非按文件是否属于第三方区分。

本计划允许新增必要的薄调用脚本、配置、补丁、有限功能检查和项目模板；不允许重建通用代理平台、另造情感引擎、无需要求数据库/队列/云服务/网页仪表盘，或为一个样本部署 GPU 模型。

审查只抓会造成错误生产、事实越界、成本风险、漏功能和假验收的问题。每个修复必须有失败原因及受影响验证；不要求每个命令单独生成一份证据报告。源代码未变、输入未变、证据已核查的完成阶段直接复用。

内容生成遵循 CNW 本来的职责边界，项目数据必须自行填写；不能因“不改上游”而不敢提供作品名称、中文语言、角色知识、场景范围或输入正文。不能把上游示例小说的人物及剧情当成通用方法复制。

更新计划时同时更新所有实际活动入口，仓库中不得有两个生效总计划。当前活动计划为 `plans/MASTER_PLAN_GENERIC_APP_R5.md`；P2/P3/P3.1 的计划和 J19 范围均保留历史身份，不得重新激活。固定 SHA 是来源身份，不是“只准用带 bug 的可执行物”。部署身份必须另带补丁及依赖锁。活动阶段由独立只读 Controller 按当前计划签收；唯一 `main` 之外不创建候选分支。
