# P2 《苍歧》单场生产规范

## P1. 我们交付什么

一场能放回既有剧情里连着读的君天离单 POV 日常戏。它需要有具体人物行动和现场反应，不是设定摘要，不是情绪说明，不是“他们聊得很开心”的梗概。篇幅由场景完成度决定，不为凑固定字数填充。

交付以中文为第一版本，延续当前已指定的 JUN-SINGLE-02.3 项目材料。日本发行、日语翻译、美术和 Godot 演出实装不在这次文本生产工程里额外展开。需要承接到 AVG 的台词/行动划分可保留，但不要为了输出脚本格式把场景写成空洞工单。

## P2. Canon 与新增创作分开

在私有 CNW 项目实例 `workspace/cangqi/` 中使用原通用模板，写入以下项目数据：

| 文件/区域 | 必须包含 | 事实来源 |
|---|---|---|
| `90_canon/canon.md` | 原稿身份、主 POV、硬规则索引、固定锚/分支约束 | 原包版本及合同 |
| `90_canon/character_bible.md` | 出场人物、关系、称呼、说话方式、当期行动依据 | 真实角色/场景文本 |
| `90_canon/world_bible.md` | 本场涉及的地点、礼制、物件能力、时空规则 | 原稿，不补百科式新设定 |
| `90_canon/glossary.md` | 专名、人称、称谓、同物异名 | 原稿及既有术语表 |
| `90_canon/timeline.md` | 场景时间、前后状态、条件分支、信息披露点 | 场景 manifest 和实际正文 |
| `92_style_engine/style_guide.md` | 本项目叙述/对白节奏、语言、已有风格特征 | 当前源稿及用户要求 |
| `92_style_engine/character_voice_samples.md` | 本场人物的真实短对话参考及来源 | 仅私有保存原稿短片段 |
| `92_style_engine/forbidden_patterns.md` | 本项目真实发现的表层/结构/语义问题 | 不照搬示例小说专属黑名单 |

原作者明确允许用自己的角色、世界、语言和文体替换模板实例 [S02]；填写这些不是破坏原工作流。

事实条目可用 `CONFIRMED / INFERRED / TODO_CONFIRM`；新增日常设计另外标 `PROPOSED_SCENE_DETAIL`。新增局部布景和动作可以用于候选场景，但不能反写源 Canon 为“原著本来就有”。

给写作模型的 `active_canon.json` 只包含当前场景需要的信息和君天离合法可获得的信息。审查者可读完整秘密/后文，正文生产者不要被动吃整部作品的所有秘密再被要求“假装不知道”。为避免提前泄密可以给禁止披露的主题/边界，不能把具体秘密原文塞进正文 prompt。

遵循 CNW 的“写作代理不直接读全部 forbidden_patterns、由检查处理”的职责分离：风格禁用模式清单留给校验阶段；正文 Brief 仍必须包含当前场景的 Canon 硬边界和正向文体要求。这两者不冲突。

## P3. 源稿定位和安全导入细节

已记录原 ZIP SHA256：`300A829C7524D620AB89177AFCF52C03DFFEA633392C632F69A943F798DAD3B2`。

优先读现有已验证路径。没有才用 Known Folder：

```powershell
$Guid = '{374DE290-123F-4565-9164-39C4925E467B}'
$Key = 'HKCU:\Software\Microsoft\Windows\CurrentVersion\Explorer\User Shell Folders'
$Folders = Get-ItemProperty -LiteralPath $Key
$Downloads = [Environment]::ExpandEnvironmentVariables($Folders.$Guid)
if (-not (Test-Path -LiteralPath $Downloads)) {
    # 改用系统 Known Folder API，或已有的明确用户输入路径。
    # 不能默默把猜测的 C:\Users\... 路径当已验证。
    throw 'DOWNLOADS_LOCATION_UNRESOLVED'
}
```

搜索时只读 ZIP，权限失败记下实际未覆盖子路径，不把未读目录宣称已搜完。哈希匹配之后先枚举成员，再安全解压。ZIP 安全检查是导入工具的一次功能，不创建新的审计平台。

`source_manifest.json` 保存 ZIP 身份、实际成员路径、大小和 SHA256；相同输入之后复用该 manifest。`source_index.json` 每场保存入口/出口、角色、时间/分支和知识变化，引用正文片段的位置。实现不强制改变原包字段名，只做显式映射。

若真实源与旧计划数量/字段不一致，先依据同哈希源修正读取逻辑。不能为了满足旧报告“32 场”制造不存在的内容；若确实换了源版本，必须把版本差异当真实输入变化处理。

## P4. 选择一场，不生成海量候选

Writer 完整读相邻剧情及人物资料，选一个满足以下事实条件的插入点：

- 场景人物有合理的共处时间与地点，君天离能亲历该事。
- 不需要添加新历史、新阵营关系或剧透，下一固定锚的输入状态可以保持。
- 场景内有可执行的小事，而不是只靠互相自我介绍或讲世界观撑满对白。

这些是本项目的样本设计约束，不假称 NK/CritiCS 已预定义该位置。地点、人物、事件必须从真实源稿决定，本方案不虚构一个未经阅读的 Jxx 插入点。

选定后填写一个 `sample_contract.json`，字段至少包括：

```text
sample_id
source_release_sha256
source_version
preceding_anchor_ref / following_anchor_ref
branch_condition (if any)
start_state / required_end_state
pov_character = 君天离
participants
location / time_window
known_to_pov / observable_to_pov
protected_canon_refs
allowed_local_changes
scene_event
scene_purpose
language
source_citations
```

`scene_purpose` 不是抽象“提升感情”。应写成可见结果，例如“通过某次实际配合，让读者看到两人处理同一问题的差别”；具体人物、事件依源填写。可以有轻微关系印象变化，但不能提前实现原剧情后面才会发生的重大转变。

Controller 选择最有源依据且可闭合的一个，不要求 24 个备选再评分。若第一个位置确实有硬冲突，选另一个已经审过源的合法位置；不是因为一次不适用就宣布“无合法样本”。

## P5. CNW 产物如何填写

实际从固定 CNW 的 `templates/06_plot`、`templates/05_scene_cards`、`templates/07_draft` 获取模板文件；文件名以目录实存为准，不猜不存在的模板。文件编号沿原方法 [S01]，内容使用当前项目。

### 1. Plot

保存 `06_plot/ep001_plot.v0.md`。用当前样本合同与源事实填原 Plot 模板；描述本场起始行动、人物回应、局势变化与结束状态。必须能回答：为什么现在发生、谁推动、产生什么可见变化、如何回到下一锚。

这是提纲层，不能把一大段提前写好的正文塞到 Plot 伪装模板已完成。也不能因为原 CritiCS `applyQA` 允许加场就把本场擅自扩成一章。

### 2. 实际 CritiCS 剧情批评与修改

`three_critic()` 返回的 structure、ending、original、inspector 全部保存 [S04]。这里的 ending 是本场事件落点，不是强行改写整部《苍歧》的终局。项目范围通过输入上下文显式限定，不删除原“结尾批评”维度。

运行 `modifiedStoryline()` 后，Controller 对照合同判断哪些修改仍合法。要有当前接受的 Plot 文件及版本，其他候选仍保留。禁止跳过该真实修改路径、只让 Writer 自己“参考意见改一下”却说原修改函数已执行。

### 3. Scene Card

保存 `05_scene_cards/ep001_scene_cards.md`。一张卡覆盖这一场，内部可分行动节拍，不扩成额外场次。原模板字段之外确有必要的项目字段可附加，并标项目适配：

- 起始状态、人物各自局部意图、可见行动和反应。
- 君天离从哪里看到/听到信息，什么只能是推测。
- 当前小事件的障碍、变化和落点；不得都写成情绪标签。
- 一旦触及原剧情秘密/分支/身份，引用保护边界。
- 结束时位置、物件、知识、关系及时间如何衔接下一原场。

不是新建“固定六槽”或通用数值情绪模型；这些字段只是把当前戏的具体设计交给正文生产者。

### 4. NK 请求和输出映射

真实调用 `generate-perspective`。根据原路由合同构造：
- `eventSequence`：本场事件/动作内容，不只放“吃饭、聊天”等标签。
- `perspectives[0].narrator`：君天离。
- `eventObjective`：本场行动目的和单场范围。
- `characterSnapshots`：只有源支持并允许当前 POV 使用的特征。
- `customPrompt`：中文、受限视角、保持原作边界等项目输入。

保存请求、原 response、schema 验证和 `nk_to_brief_map.json`。映射至少指明：NK 某段内容如何形成 Brief 的观察角度/反应/角色表现要求，引用对应文本而非只给同一个 hash。

NK 输出若越界，不强行往成品里塞；先修正输入或具体输出问题，再获得合格材料。若整份输出完全没被使用，这次不能写 `NK_CONTRIBUTION_VERIFIED`。

### 5. Writing Brief

保存 `07_draft/ep001_writing_brief.md`。遵循原 Brief 的头部、活动 Canon、逐场信息和硬约束结构，包含：

当前源/Plot/Card 的版本，前后原文边界，人物当期称呼与说话参考，已核准 NK 视角材料，每个行动节拍的目的、必须保持的结束状态，中文输出及“完整正文而非概述”的要求。

Brief 不包含无关全剧秘密、不复制作者示例小说、不用几句“自然一点、有趣一点”代替具体设计。控制器检查 input bundle 的实际文本，不只检查各路径存在。

### 6. Prose

保存 `07_draft/episodes/ep001.v0.md`。Flash 按 Brief 输出完整戏，保留对话、动作、当下感知和必要叙述；君天离之外的心理不能以确定事实直写。可以写他观察到的神色、停顿、行为及基于观察的推断。

不得输出“此处展开对话”“接下来两人和解”等占位符；不能以总结式旁白代替全部表演；不能无依据堆砌关系升级、煽情或笑话。文字风格应与源稿相邻部分匹配。

## P6. 文字审查、意见应用和全场验收

### 原工具做其真实负责的部分

CritiCS 的 Image/Voice 对关键句段提出修改，Leader 选择有效建议 [S05]。本次默认选取承载行动转折或人物差异的真实连续句段（不超过五句），输入和所在全文行段要记录。不要随机选无关描述来“打卡用过工具”。

保留 Image/Voice 原维度；Voice “informal/netspeak”等是原批评视角，不代表必须往古风人物嘴里塞“lol”。项目文体和 Canon 保持优先，意见可拒绝但理由具体。

### CNW Revision 应用有效意见

保存 `08_review/ep001_tool_review.md` 和 `09_revision/ep001_revision_plan.md`；意见表只保留几项实质内容：原反馈位置、涉及正文、决定、理由、修改后位置。由 Flash 产出 `ep001.v1.md`。可逆细节自己修，不回问用户每一句。

没有实质有效意见时，不能为了证明“使用过”强行制造更差改动。保留“不采用”的依据，并让 Controller 判断是否确实无必要修改；不能把这个例外用于跳过全部反馈。

### CNW 三层检查落实到本场，而不新建评审平台

沿 CNW 的原三层职责 [S02]：第一层由 Writer 运行有限的表层检查（占位符、模板残留、已确认术语和格式）；第二层把带上下文的命中交给 Controller 判断是否误报，不能看到一个关键词就机械删句；第三层由独立 Controller 对完整场景作语义与 Canon 审阅。每项问题允许被原文反证；只有证据成立的问题进入 Revision，最后再检查是否遗漏了必须发生的行动和衔接。

三个层次是检查职责，不要求再造三个执行框架或强行并发多个工程验收 agent；未发现本项目相应禁用模式时不照搬示例小说规则凑数。工具的局部批评不能替代这套全场检查。

### 全场检查不能交给局部句段工具冒充

Controller 读完整连读版，依以下可观察标准判断，而不是给假客观总分：

| 检查 | 合格表现 | 不合格例子 |
|---|---|---|
| 原作一致 | 原稿人物、时间、地点、物件能力和后续状态不被改坏 | 下一场应不知道的秘密已被揭开 |
| 受限 POV | 所有新信息可由君天离感知或合理推测 | 直接断言另一角色隐藏动机 |
| 戏的完整性 | 有具体事发生，有行动、回应与落点 | 大段心情总结，没有可发生的行为 |
| 人物区分 | 台词、选择和反应符合各人，不靠名字区分同一种说话模板 | 换人名仍完全成立的泛化对话 |
| 节奏与用途 | 相邻对白/动作推动小事件或人物理解 | 连续重复同一感受、设定灌输 |
| 前后衔接 | 新场入口出口与两侧锚一致，读者不必脑补位置跳变 | 突然出现/消失的道具和人物 |
| 文体 | 延续本项目风格，无模板残留和生硬工具痕迹 | “作为角色”“情绪值变化”留进正文 |
| 工具参与 | 实际返回进入设计/Brief/修订，作用范围如实 | 克隆了工具但正文全由另一套方法产生 |

“用户最终觉得好不好看”仍由用户自己决定。Controller 有责任先把上述明显问题修掉，不能把未完成的草稿当“反正用户判断”交差。

## P7. 修复由什么错误决定

- 开始就不知道角色动机：回到源事实/合同，不盲修措辞。
- Plot 无实际事件：回到 Plot，不重装依赖。
- 事件有但正文平：检查 Scene Card/Brief 有没有可演出的行动信息，定点改写。
- 某一句读心/提前泄密：修该句及受影响反应；若泄密来自整个输入包，修输入并重验下游。
- NK output 未进 Brief：修映射，不额外调用 NK 多次凑数量。
- CritiCS 反馈通用空泛：查是否确实传入本场正文及当前 Plot；先排除漏输入，再考虑模型输出质量。
- 输出截断/乱码：修传输、输出额度或编码，保留原失败；不降低正文完成要求。
- 相同意见反复出现：Controller 明确最早因果环节，修原因后再运行对应下游；不重做治理。

## P8. 可读交付格式

最终目录：`deliverables/<sample-id>/`。

```text
00_阅读说明.txt
01_初稿.txt
02_修订稿.txt
03_前后文连读.html
03_前后文连读.md
03_前后文连读.txt
04_修改说明.md
05_本地复用说明.md
artifact_manifest.json
```

连读版含足够理解当前段落的前文、完整新增场景和实际衔接后文；三部分边界清楚，不能裁掉导致矛盾的原句来显得自然。不要求复制整部剧本。

HTML 正确转义原文，内置必要样式，无外链依赖，无正文截断；TXT 采用 UTF-8（Windows 阅读版可带 BOM），Markdown 使用 UTF-8。按真实文件存在情况报告路径，不能只给用户一个不存在的“下载链接”。本地故事文件不进入公开 Git。

复用说明使用已经实现并验证的入口，记录所需环境变量名、启动方式和断点恢复，不包含 Key 值。下一场未来获用户授权后只更换场景合同与输入，不重新搭工具；本次仅验证加载已有样本和导出，不自动做第二场。
